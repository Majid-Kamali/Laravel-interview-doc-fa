بخش ۱: PHP — OOP پایه

Interface vs Abstract Class

این یکی از پرتکرارترین سوالات مصاحبه‌ست، چون خیلی‌ها تفاوتش رو سطحی بلدن.

Interface

  • فقط قرارداد (contract) — امضای متدها، بدون implementation
  • یک کلاس می‌تونه چند Interface رو implement کنه (multiple implementation)
  • نمی‌تونه property با مقدار داشته باشه (فقط constant)
  • private , protected را نمی توانیم استفاده کنیم
  • از php 8 به بعد قابلیت استفاده از static رو داریم
  • نمی توان متد public اینترفیس را private در فرزند تعریف کرد
interface PaymentGatewayInterface
{
    public function charge(int $amount): bool;
    public function refund(string $transactionId): bool;
}

Abstract Class

  • می‌تونه هم متد abstract (بدون بدنه) و هم متد concrete (با بدنه) داشته باشه
  • یک کلاس فقط می‌تونه از یک Abstract Class extend کنه (single inheritance)
  • می‌تونه property و constructor داشته باشه
abstract class Notification
{
    protected string $channel;

    abstract public function send(string $message): void;

    public function log(string $message): void
    {
        // این متد مشترک بین همه فرزندهاست
        Log::info("Sending via {$this->channel}: {$message}");
    }
}
نکته کلیدی مصاحبه: سوالی مثل «چرا Interface و نه Abstract Class؟» معمولاً می‌خواد این رو بشنوه: از Interface وقتی استفاده می‌کنیم که چند کلاس بی‌ربط به هم (از نظر سلسله‌مراتب) باید یک رفتار مشترک رو implement کنن — مثلاً StripeGateway و ZarinpalGateway هیچ ارتباط والد-فرزندی ندارن، فقط قرار قراردادی مشترک دارن.

مثال عملی

فرض کنیم سیستم پرداخت داریم:

interface PaymentGateway
{
    public function pay(int $amount): bool;
}

دو پیاده‌سازی:

class StripeGateway implements PaymentGateway
{
    public function pay(int $amount): bool
    {
        return true;
    }
}

class ZarinpalGateway implements PaymentGateway
{
    public function pay(int $amount): bool
    {
        return true;
    }
}

و Service:

class OrderService
{
    public function __construct(private PaymentGateway $gateway)
    {
    }
}

در Laravel:

$this->app->bind(PaymentGateway::class, StripeGateway::class);

تفاوت اصلی در یک جمله

Interface برای تعریف قابلیت‌ها (capabilities) است، Abstract Class برای اشتراک رفتار (shared behavior).
در Laravel معمولاً Interface را ترجیح می‌دهم چون Service Container روی Interface Binding کار می‌کند، تست کردن با Mock بسیار ساده‌تر می‌شود، کلاس‌ها به Implementation وابسته نیستند و می‌توانم بدون تغییر Consumer، پیاده‌سازی را جایگزین کنم. Abstract Class را فقط زمانی استفاده می‌کنم که واقعاً منطق مشترک قابل توجهی بین کلاس‌ها وجود داشته باشد.

سوال رایج

می‌تونیم توی interface ها از protected استفاده کنیم؟

خیر، در PHP نمی‌توانیم در Interface از protected یا private استفاده کنیم.

Trait

راه‌حل PHP برای "multiple inheritance" (چون PHP از ارث‌بری چندگانه کلاس پشتیبانی نمی‌کنه): 

trait Loggable
{
    public function logActivity(string $action): void
    {
        Log::info(static::class . ": {$action}");
    }
}

class Order
{
    use Loggable;
}
نکته مهم: اگه دو Trait متد هم‌نام داشته باشن و هر دو use بشن، تضاد پیش می‌آد و باید با insteadof حلش کنی — این یه سوال ریز ولی رایجه.

Namespace و Composer Autoload

۱. Namespace چیست؟

در PHP وقتی پروژه بزرگ می‌شود، احتمال دارد دو کلاس با یک نام داشته باشیم.

در یک پروژه: App\Models\User و Package\Auth\User

هر دو اسمشان User است و PHP نمی‌داند کدام را استفاده کند.

Namespace برای جلوگیری از تداخل نام کلاس‌ها و سازمان‌دهی کد ساخته شده است.

۲. Composer Autoload چیست؟

اگر کلاس را import کردیم:

use App\Models\User;

PHP از کجا بفهمد فایل User.php کجاست؟ اینجا Composer وارد می‌شود.

Composer یک سیستم Autoload دارد که مشخص می‌کند کلاس App\Models\User در کدام فایل قرار دارد.

PSR-4 Autoloading

Laravel از استاندارد PSR-4 استفاده می‌کند. در فایل composer.json می‌بینیم: 

{
    "autoload": {
        "psr-4": {
            "App\\": "app/"
        }
    }
}

معنی: هر کلاسی که با App\ شروع شود، داخل پوشه app/ جستجو شود.

Autoload چگونه اجرا می‌شود؟

وقتی Laravel شروع می‌شود، فایل public/index.php را اجرا می‌کند. یکی از اولین کارها: 

require __DIR__.'/../vendor/autoload.php';

این فایل توسط Composer ساخته شده. بعد از آن PHP می‌تواند کلاس‌ها را خودکار پیدا کند.

composer dump-autoload چیست؟

وقتی کلاس جدید اضافه می‌کنی (مثلاً app/Services/PaymentService.php)، گاهی Composer هنوز آن را نمی‌شناسد. اجرا می‌کنیم: 

composer dump-autoload

Composer دوباره Mapping کلاس‌ها را تولید می‌کند. در Laravel معمولاً:

composer dump-autoload -o

یعنی Optimized Autoload — برای Production بهتر است.

تفاوت include/require با Autoload

روش مشکل
require 'PaymentService.php'; مدیریت فایل‌ها سخت، وابستگی زیاد، مناسب پروژه بزرگ نیست
Autoload $service = new PaymentService(); — خودکار لود می‌شود

Namespace و Autoload چه ارتباطی دارند؟

Namespace نام کامل کلاس را مشخص می‌کند، اما Autoload مشخص می‌کند این کلاس در کدام فایل قرار دارد. Composer با استفاده از Namespace و PSR-4 Mapping فایل کلاس را پیدا و Load می‌کند.
Namespace در PHP برای سازمان‌دهی کلاس‌ها و جلوگیری از collision استفاده می‌شود و Composer Autoload وظیفه بارگذاری خودکار این کلاس‌ها را دارد. Laravel از PSR-4 autoloading استفاده می‌کند؛ در composer.json یک mapping بین namespace و directory تعریف می‌شود. هنگام اجرای برنامه، vendor/autoload.php بارگذاری می‌شود و Composer بر اساس namespace کلاس موردنظر را پیدا می‌کند، بنابراین دیگر نیازی به require کردن دستی فایل‌ها نداریم.

Throwable چیست؟

از PHP 7 به بعد یک Interface اصلی داریم: Throwable. این بالاترین سطح برای چیزهایی است که می‌توان با catch گرفت. 

catch (Throwable $e)

می‌تواند هم Exception و هم Error را دریافت کند.

تفاوت Exception و Error

نوع توضیح مثال
Exception معمولاً مشکل منطقی یا شرایط غیرمنتظره‌ی برنامه است. قابل پیش‌بینی است. throw new Exception("Payment failed")
Error معمولاً مشکل در خود کد یا موتور PHP است. TypeError — وقتی int انتظار داریم ولی string گرفتیم 
function add(int $a)
{
    return $a;
}

add("hello"); // TypeError
Laravel تقریباً تمام خطاها را از طریق Exception Handler مدیریت می‌کند.

Custom Exception در Laravel

class PaymentFailedException extends Exception
{
}

استفاده:

if (!$paymentSuccessful) {
    throw new PaymentFailedException("Payment failed");
}

بعد در Handler:

public function render($request, Throwable $exception)
{
    if ($exception instanceof PaymentFailedException) {
        return response()->json([
            'message' => $exception->getMessage()
        ], 400);
    }
}
در PHP هر چیزی که قابلیت throw شدن و catch شدن داشته باشد زیرمجموعه Throwable است. Exceptionها معمولاً خطاهای قابل مدیریت در منطق برنامه هستند، مثل Validation یا خطای پرداخت. Errorها بیشتر مربوط به مشکلات سطح زبان PHP هستند، مثل TypeError یا ParseError. در Laravel معمولاً Exceptionها را مدیریت می‌کنیم، اما برای جلوگیری از crashهای غیرمنتظره می‌توانیم Throwable را در سطح بالاتر catch کنیم.

Type Hinting / Union Types / Enums

Union Type (PHP 8+)

function process(int|string $id): void {}

Enum (PHP 8.1+)

enum PaymentStatus: string
{
    case Pending = 'pending';
    case Success = 'success';
    case Failed = 'failed';
}
سوال رایج مصاحبه: تفاوت Pure Enum و Backed Enum — Backed Enum مقدار اسکالر (مثل رشته یا int) داره و می‌تونی از PaymentStatus::from('pending') استفاده کنی؛ Pure Enum فقط case داره بدون مقدار.

Closures

$multiplier = function (int $x) use ($factor) {
    return $x * $factor;
};

// Arrow function (PHP 7.4+) — use خودکاره
$multiplier = fn($x) => $x * $factor;

Closure چیست؟

یک تابع بدون نام (Anonymous Function) که می‌تواند به عنوان یک متغیر ذخیره شود، به تابع دیگری ارسال شود یا حتی متغیرهای محیط بیرونی خودش را به خاطر بسپارد.

نام ندارد و فقط از طریق متغیر قابل دسترسی است.

استفاده از Closure در Laravel

  • Route
  • Collection
  • Middleware
  • Database Transaction
DB::transaction(function () {
    Order::create([
        'user_id' => 1
    ]);
});

Capture by Value vs Reference

مقدار را هنگام ساخت Closure کپی می‌کند:

$count = 10;

$closure = function () use ($count) {
    return $count;
};

$count = 20;

echo $closure(); // 10

اگر بخواهیم مقدار اصلی تغییر کند (با Reference):

$count = 10;

$closure = function () use (&$count) {
    $count++;
};

$closure();

echo $count; // 11
& یعنی با Reference بگیر.
Closure یک anonymous function در PHP است که می‌تواند به عنوان callback استفاده شود و قابلیت capture کردن متغیرهای محیط بیرونی را دارد. در Laravel به صورت گسترده در Route definitions، Collections، Database Transactions، Middleware و Event handling استفاده می‌شود. مزیت آن این است که می‌توانیم رفتار را به صورت داینامیک به بخش‌های مختلف برنامه ارسال کنیم.

Pure Enum vs Backed Enum

Pure Enum چیست؟

Pure Enum فقط شامل case است و هیچ مقداری ندارد.

enum PaymentStatus
{
    case Pending;
    case Paid;
    case Failed;
}

استفاده:

$status = PaymentStatus::Paid;

Backed Enum چیست؟

Backed Enum علاوه بر case، یک مقدار واقعی دارد. این مقدار باید یکی از این دو باشد: string یا int 

enum PaymentStatus: string
{
    case Pending = 'pending';
    case Paid = 'paid';
    case Failed = 'failed';
}

حالا:

$status = PaymentStatus::Paid;
echo $status->value; // "paid"

چرا در Laravel از Backed Enum بیشتر استفاده می‌کنیم؟

در پروژه‌های Laravel معمولاً از Backed Enum استفاده می‌کنم چون مقادیر آن قابل ذخیره در Database هستند و با Eloquent Casting به صورت type-safe کار می‌کنند. این باعث می‌شود از مقدارهای اشتباه جلوگیری شود و کد خواناتر و قابل نگهداری‌تر باشد.

Pure Enum چه زمانی استفاده می‌شود؟

مثلاً وقتی فقط مفهوم مهم است، نه مقدار:

enum UserRole
{
    case Admin;
    case Customer;
    case Guest;
}
Pure Enum فقط شامل caseها است و هیچ مقدار scalar ندارد، بنابراین برای زمانی مناسب است که فقط یک مجموعه ثابت از حالت‌ها می‌خواهیم. اما Backed Enum علاوه بر case دارای مقدار string یا int است و برای سناریوهایی مثل ذخیره در Database مناسب‌تر است. در Laravel معمولاً Backed Enum استفاده می‌کنم چون با Eloquent Casts می‌توانیم مقدارهای Database را به Enum تبدیل کنیم و از type safety استفاده کنیم.

بخش ۲: SOLID Principles

این پنج اصل جزو پرتکرارترین سوالات مصاحبه‌ی بک‌اند هستن — نه فقط تعریف، بلکه انتظار دارن با مثال کد واقعی از پروژه Laravel توضیح بدی.

S — Single Responsibility Principle (SRP)

هر کلاس فقط باید یک دلیل برای تغییر داشته باشه.

❌ نقض SRP

class Order
{
    public function calculateTotal(): float { /* ... */ }
    public function saveToDatabase(): void { /* ... */ }
    public function sendConfirmationEmail(): void { /* ... */ }
}

این کلاس هم منطق محاسبه، هم persistence، هم notification رو داره — سه دلیل مختلف برای تغییر.

✅ رعایت SRP

class Order { /* فقط منطق دامنه سفارش */ }

class OrderRepository
{
    public function save(Order $order): void {}
}

class OrderConfirmationNotifier
{
    public function notify(Order $order): void {}
}

O — Open/Closed Principle (OCP)

کلاس باید برای extension باز و برای modification بسته باشه.

❌ نقض OCP

class PaymentProcessor
{
    public function process(string $type, float $amount)
    {
        if ($type === 'stripe') { /* ... */ }
        elseif ($type === 'paypal') { /* ... */ }
        // هر gateway جدید یعنی دوباره این کلاس رو تغییر بدی
    }
}

✅ رعایت OCP (با Interface)

interface PaymentGatewayInterface
{
    public function process(float $amount): bool;
}

class StripeGateway implements PaymentGatewayInterface { /* ... */ }
class PaypalGateway implements PaymentGatewayInterface { /* ... */ }

class PaymentProcessor
{
    public function __construct(private PaymentGatewayInterface $gateway) {}

    public function process(float $amount): bool
    {
        return $this->gateway->process($amount);
    }
}

حالا برای gateway جدید فقط یک کلاس جدید اضافه می‌کنی، PaymentProcessor رو دست نمی‌زنی.

L — Liskov Substitution Principle (LSP)

فرزند باید بتونه بدون تغییر رفتار مورد انتظار، جای والدش بنشیند.

❌ نقض LSP (مثال کلاسیک)

class Rectangle
{
    protected float $width;
    protected float $height;

    public function setWidth(float $w): void { $this->width = $w; }
    public function setHeight(float $h): void { $this->height = $h; }
    public function area(): float { return $this->width * $this->height; }
}

class Square extends Rectangle
{
    public function setWidth(float $w): void
    {
        $this->width = $this->height = $w; // رفتار غیرمنتظره!
    }
}

اگه کدی Rectangle $shape بگیره و انتظار داشته باشه setWidth(5); setHeight(10); بده area() == 50، ولی Square بجاش بده، رفتار غلط می‌شه.

I — Interface Segregation Principle (ISP)

کلاس‌ها نباید مجبور شن متدهایی رو implement کنن که به کارشون نمی‌آد.

❌ نقض ISP

interface Worker
{
    public function work(): void;
    public function eat(): void;
}

class RobotWorker implements Worker
{
    public function work(): void { /* ... */ }
    public function eat(): void { throw new Exception('Robots do not eat!'); } // مجبور شده implement کنه
}

✅ رعایت ISP

interface Workable { public function work(): void; }
interface Eatable { public function eat(): void; }

class HumanWorker implements Workable, Eatable {}
class RobotWorker implements Workable {}

D — Dependency Inversion Principle (DIP)

ماژول‌های سطح بالا نباید به ماژول‌های سطح پایین مستقیم وابسته باشن؛ هر دو باید به abstraction وابسته باشن.

این دقیقاً همون مثال PaymentProcessor بالاست — PaymentProcessor (سطح بالا) به PaymentGatewayInterface (abstraction) وابسته‌ست، نه به StripeGateway مستقیم (سطح پایین). این اصل پایه‌ی کل Service Container لاراول هست.

بخش ۳: اصول SOLID به زبان ساده (توضیح عمیق‌تر)

۱. اصل تک مسئولیتی (Single Responsibility Principle)

هر کلاسی که توی برنامه‌ی ما وجود داره، باید یک مسئولیت خاص و مشخص داشته. در واقع این کلاس باید فقط و فقط مسئول یک عملکرد توی برنامه باشه.

مثال نقض SRP

class User {
    public function information() {}
    public function sendEmail() {}
    public function orders() {}
}

توی این کلاس ما سه تا متد داریم. متد information که اطلاعات کاربر رو برمیگردونه. متد sendMail برای ارسال ایمیل به کاربر و متد orders سفارش‌های کاربر رو برمی‌گردونه.

کلاس User نباید مسئول ارسال ایمیل و یا هندل کردن سفارشات کاربر باشه. در این صورت کلاس ما با عملکردهای ذاتی خودش محصور شده نیست. یعنی کلاس User با یک سری عملکردهای غیرمرتبط آمیخته شده.

این مسئله زمانی مشکل‌ساز میشه که می‌خوایم کلاس رو گسترش بدیم. مثلاً ایمیل‌های مختلف و اختصاصی‌تر بفرستیم. که آخر کار نمی‌دونیم این کلاس User هست یا Email!

راه حل

class User {
    public function information() {}
}

class Email {
    public function send(User $user) {}
}

class Order {
    public function show(User $user) {}
}

همونطور که می‌بینید، کلاس User ما خلوت‌تر، تمیزتر و مرتب تر شد. همچنین توسعه این کلاس و کلاس‌های دیگه راحت‌تر انجام میشه.

نکته: این اصل نه تنها توی سطح کلاس‌ها، بلکه توی سطح متدها و توابع هم می‌تونه اعمال بشه.

مثال نقض SRP در سطح متد

class Mailer {
    public function send($text) {
        $mailer = new Mail();
        $mailer->login();
        $mailer->send($text);
    }
}

متد send مسئول انجام ۲ کار هست: احراز هویت و بعد ارسال ایمیل. همچنین اصل دوم SOLID (OCP) هم اینجا نقض شده.

راه حل

class Mailer {
    private $mailer;

    public function __construct($mailer) {
        $this->mailer = $mailer;
    }

    public function send($text) {
        $this->mailer->send($text);
    }
}

$myEmail = new MyEmailService();
$myEmail->login();

$mail = new Mailer($myEmail);
$mail->send('Salut');

همونطور که می‌بینیم، متد send فقط کاری رو انجام میده که وظیفه‌ اون هست.

۲. اصل باز - بسته (Open/Closed Principle)

موجودیت‌های یک نرم‌افزار (کلاس‌ها، ماژول‌ها، توابع و ...) باید برای توسعه داده شدن، باز و برای تغییر دادن، بسته باشن.

اصل OCP میگه که ما باید کد رو جوری بنویسیم که وقتی می‌خوایم اون رو توسعه بدیم و ویژگی‌های جدید اضافه کنیم، مجبور نشیم اون رو تغییر بدیم و دستکاری کنیم. ویژگی‌های جدید باید براحتی و بدون دستکاری کردن قسمت‌های دیگه اضافه بشن.

شما باید بتوانید قابلیت جدیدی به سیستم اضافه کنید، بدون اینکه حتی یک خط از کدهای قدیمی و تست‌شده را دستکاری کنید.

تفکیک مفهوم "باز" و "بسته"

  • باز برای گسترش (Open for Extension): یعنی باید طوری طراحی کنید که با اضافه شدن نیازمندی جدید، به جای ویرایش کلاس اصلی، یک کلاس جدید بنویسید و آن را به سیستم وصل کنید (مثلاً از طریق اینترفیس یا وراثت).
  • بسته برای تغییر (Closed for Modification): یعنی وقتی یک کلاس نوشته شد، دیباگ شد و در محیط پروداکشن قرار گرفت، نباید دوباره داخل آن بروید و کدهای آن را تغییر دهید. چون هر تغییری در کد قدیمی، ریسک ایجاد باگ جدید در بخش‌هایی که قبلاً کار می‌کردند را به همراه دارد.

❌ حالت نقض (بد) — با شرط if/else

// کلاسی که نوع شکل را با یک پراپرتی مشخص می‌کند (طراحی ضعیف)
class BadShape
{
    public string $type;
    public ?float $side = null;   // برای مربع
    public ?float $radius = null; // برای دایره
}

class BadAreaCalculator
{
    public function calculate(BadShape $shape): float
    {
        if ($shape->type === 'square') {
            return $shape->side ** 2;
        } elseif ($shape->type === 'circle') {
            return 3.14 * ($shape->radius ** 2);
        }
        // اگر فردا بخواهیم شکل "مثلث" اضافه کنیم، باید این متد را ویرایش کنیم!
        throw new Exception("Shape type not supported");
    }
}

// استفاده
$square = new BadShape();
$square->type = 'square';
$square->side = 5;

$calculator = new BadAreaCalculator();
echo $calculator->calculate($square); // خروجی: 25

✅ حالت صحیح (خوب) — با استفاده از اینترفیس

// 1. یک اینترفیس (قرارداد) تعریف می‌کنیم
interface Shape
{
    public function area(): float;
}

// 2. هر شکل، کلاس مجزای خودش را دارد که اینترفیس را پیاده‌سازی می‌کند
class Square implements Shape
{
    public function __construct(private float $side) {}

    public function area(): float
    {
        return $this->side ** 2;
    }
}

class Circle implements Shape
{
    public function __construct(private float $radius) {}

    public function area(): float
    {
        return pi() * ($this->radius ** 2);
    }
}

// 3. کلاس محاسبه‌گر دیگر هیچ چیزی از جزئیات اشکال نمی‌داند
class AreaCalculator
{
    // ورودی از نوع اینترفیس است، نه یک کلاس مشخص
    public function calculate(Shape $shape): float
    {
        return $shape->area();
    }
}

// --- استفاده از کد ---
$square = new Square(5);
$circle = new Circle(3);

$calculator = new AreaCalculator();

echo $calculator->calculate($square); // خروجی: 25
echo $calculator->calculate($circle); // خروجی: 28.27

۳. اصل جایگزینی لیسکوف (Liskov Substitution Principle)

اگر S یک زیر کلاس T باشه، آبجکت‌های نوع T باید بتونن بدون تغییر دادن کد برنامه، با آبجکت‌های نوع S جایگزین بشن.

به بیان ساده‌تر: کلاس‌های فرزند نباید رفتار و ویژگی‌های کلاس والد رو تغییر بدن.

یعنی اگر جایی از برنامه از کلاس والد استفاده می‌کنیم، بتوانیم کلاس فرزند را جای آن قرار دهیم بدون اینکه رفتار برنامه خراب شود.

مثال ساده

class Bird
{
    public function fly(): void
    {
        echo "Flying";
    }
}

class Sparrow extends Bird
{
}

function makeBirdFly(Bird $bird)
{
    $bird->fly();
}

makeBirdFly(new Sparrow()); // هیچ مشکلی ندارد

توضیح

LSP می‌گوید هر کلاس فرزند باید بتواند بدون تغییر رفتار صحیح برنامه جایگزین کلاس والد شود. اگر استفاده از کلاس فرزند باعث شود کدهای وابسته به والد خراب شوند، Exception غیرمنتظره ایجاد شود یا قرارداد رفتاری تغییر کند، این اصل نقض شده است.

در Laravel این موضوع را معمولاً در Interfaceها، Repositoryها، Serviceها و Strategy Pattern رعایت می‌کنیم.

۴. اصل جداسازی اینترفیس‌ها (Interface Segregation Principle)

کلاس‌ها نباید مجبور باشن متدهایی رو implement کنن که به کارشون نمی‌آد.

هیچ کلاسی نباید مجبور شود متدهایی را پیاده‌سازی کند که به آن‌ها نیاز ندارد.

یعنی Interface باید کوچک، متمرکز و تخصصی باشد.

مثال

interface Workable
{
    public function work(): void;
}

interface Eatable
{
    public function eat(): void;
}

class HumanWorker implements Workable, Eatable
{
    public function work(): void
    {
        echo "Working";
    }

    public function eat(): void
    {
        echo "Eating";
    }
}

class RobotWorker implements Workable
{
    public function work(): void
    {
        echo "Working";
    }
}

چرا Interface کوچک بهتر است؟

چون باعث کاهش Coupling، افزایش Cohesion، تست‌پذیری بهتر و تغییرات کمتر در سیستم می‌شود.

تفاوت ISP با SRP

اصل تمرکز
SRP هر کلاس یک مسئولیت داشته باشد.
ISP هر Interface فقط قرارداد مربوط به یک مسئولیت را تعریف کند.

توضیح

ISP می‌گوید Interfaceها باید کوچک و متمرکز باشند و هیچ کلاسی نباید مجبور شود متدهایی را پیاده‌سازی کند که از آن‌ها استفاده نمی‌کند. در Laravel معمولاً به جای Interfaceهای بزرگ، Interfaceهای تخصصی مثل Reader، Writer یا PaymentGateway تعریف می‌کنیم تا وابستگی‌ها کاهش پیدا کند، تست‌ها ساده‌تر شوند و تغییرات سیستم روی بخش‌های غیرمرتبط اثر نگذارد.

۵. اصل وارونگی وابستگی (Dependency Inversion Principle)

کلاس‌های سطح بالا نباید به کلاس‌های سطح پایین وابسته باشن؛ هر دو باید وابسته به انتزاع (Abstractions) باشن. موارد انتزاعی نباید وابسته به جزییات باشن. جزییات باید وابسته به انتزاع باشن.

ماژول‌های سطح بالا نباید به ماژول‌های سطح پایین وابسته باشند؛ هر دو باید به Abstraction (Interface) وابسته باشند.
همچنین: Abstraction نباید به Details وابسته باشد؛ Details باید به Abstraction وابسته باشند.

به جای اینکه کلاس‌ها مستقیماً به کلاس‌های دیگر وابسته باشند، باید به Interface یا Contract وابسته باشند.

مثال

ابتدا Interface تعریف می‌کنیم:

interface NotificationService
{
    public function send(string $message): void;
}

پیاده‌سازی:

class EmailService implements NotificationService
{
    public function send(string $message): void
    {
        echo "Email sent: {$message}";
    }
}

OrderService:

class OrderService
{
    public function __construct(
        private NotificationService $notification
    ) {
    }

    public function createOrder()
    {
        $this->notification->send("Order created");
    }
}

الان OrderService فقط Interface را می‌شناسد.

Laravel چگونه این را حل می‌کند؟

از طریق Service Container. در Service Provider:

$this->app->bind(NotificationService::class, EmailService::class);

Controller یا Service:

class OrderController extends Controller
{
    public function __construct(private OrderService $orderService) {}
}

چرا از Interface استفاده می‌کنیم؟

برای اجرای Dependency Inversion Principle. ماژول سطح بالا نباید به جزئیات وابسته باشد. با استفاده از Interface و Service Container می‌توانیم پیاده‌سازی را تغییر دهیم، تست بنویسیم و سیستم را توسعه‌پذیر کنیم.

توضیح

DIP می‌گوید کلاس‌های سطح بالا نباید به کلاس‌های سطح پایین وابسته باشند، بلکه هر دو باید به Abstraction وابسته باشند. در Laravel این اصل با Interfaceها و Service Container پیاده‌سازی می‌شود. مثلاً OrderService به جای وابستگی مستقیم به EmailService، به NotificationService Interface وابسته می‌شود و Container پیاده‌سازی مناسب را Inject می‌کند. این کار Coupling را کاهش می‌دهد، تست‌پذیری را افزایش می‌دهد و امکان جایگزینی پیاده‌سازی‌ها را بدون تغییر کلاس‌های مصرف‌کننده فراهم می‌کند.
