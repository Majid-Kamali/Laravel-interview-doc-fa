Laravel internals – بخش اول: Request lifecycle

وقتی یک درخواست HTTP به Laravel می‌رسد، چه اتفاقی می‌افتد؟

Browser / Client
↓
Nginx / Apache
↓
public/index.php
↓
vendor/autoload.php
↓
bootstrap/app.php
↓
Application instance
↓
Service providers
↓
HTTP Kernel
↓
Middleware
↓
Router
↓
Controller
↓
Response

مرحله ۱: ورود درخواست به public/index.php

اولین فایل Laravel: public/index.php

تقریباً همه درخواست‌ها وارد این فایل می‌شوند.

اولین کار:

require __DIR__.'/../vendor/autoload.php';

این همان Composer Autoload است که قبلاً خواندیم.

بعد:

$app = require_once __DIR__.'/../bootstrap/app.php';

اینجا Application ساخته می‌شود.

مرحله ۲: ساخت Application

فایل: bootstrap/app.php

یک نمونه از کلاس: Illuminate\Foundation\Application می‌سازد.

این شیء همان Service Container هم هست.

یعنی Application فقط Application نیست؛ Container هم هست.

این نکته‌ی مصاحبه‌ای مهم است.

مرحله ۳: Service providers

بعد از ساخت Application، Laravel شروع به ثبت Service Providerها می‌کند.

مثلاً:

  • RouteServiceProvider
  • AuthServiceProvider
  • EventServiceProvider
  • AppServiceProvider

هر Provider دو متد مهم دارد:

  • register()
  • boot()

اینجا اتفاق بسیار مهمی می‌افتد.

$app->make()

یعنی: از Service Container این کلاس را Resolve کن.

پس حتی Kernel هم از طریق Container ساخته می‌شود.

مرحله ۵: ارسال Request به Kernel

$response = $kernel->handle(
    $request
);

از اینجا درخواست وارد چرخه‌ی Laravel می‌شود.

مرحله ۶: Middleware

Kernel درخواست را از میان Middlewareها عبور می‌دهد.

مثل:

  • Authenticate
  • Throttle
  • VerifyCsrfToken
  • SubstituteBindings

به این ساختار می‌گویند: Pipeline

Request
↓
Middleware 1
↓
Middleware 2
↓
Middleware 3
↓
Controller
↓
Response

Middleware می‌تواند:

  • درخواست را تغییر دهد.
  • درخواست را متوقف کند.
  • پاسخ را تغییر دهد.

مثال:

public function handle(
    $request,
    Closure $next
) {
    if (!$request->user()) {
        abort(401);
    }

    return $next($request);
}

اگر کاربر لاگین نباشد، Controller اصلاً اجرا نمی‌شود.

مرحله ۷: Router

بعد از Middleware، Router اجرا می‌شود.

مثلاً:

Route::get('/orders', [OrderController::class, 'index']);

Router تشخیص می‌دهد:

  • URI
  • Method
  • Parameters
  • Controller

مرحله ۸: Controller

Laravel Controller را از طریق Service Container می‌سازد.

class OrderController
{
    public function __construct(
        PaymentService $payment
    ) {
    }
}

Container خودش PaymentService را Inject می‌کند.

این دقیقاً Dependency Injection است.

مرحله ۹: Response

Controller ممکن است برگرداند:

return response()->json([
    'success' => true
]);

یا:

return view('orders.index');

Laravel آن را به یک: Illuminate\Http\Response تبدیل می‌کند.

مرحله ۱۰: ارسال Response

در index.php:

$response->send();

پاسخ به مرورگر ارسال می‌شود.

بعد:

$kernel->terminate(
    $request,
    $response
);

متد terminate() اجرا می‌شود.

اینجا کارهایی مثل:

  • Session
  • Logging
  • Queue dispatch
  • Terminable Middleware

انجام می‌شود.

سؤال مهم مصاحبه

اولین فایل Laravel که اجرا می‌شود چیست؟

public/index.php

چه چیزی Application را می‌سازد؟

bootstrap/app.php

چه چیزی Controller را می‌سازد؟

Service Container

Middleware قبل از Router اجرا می‌شود یا بعد؟

Middleware قبل از رسیدن به Controller اجرا می‌شود (در مسیر Kernel و Router Pipeline).

پاسخ حرفه‌ای مصاحبه

این پاسخ را حفظ نکن، مفهومش را یاد بگیر:

«درخواست از public/index.php وارد Laravel می‌شود، Composer Autoload بارگذاری می‌شود، سپس bootstrap/app.php نمونه‌ی Application و Service Container را ایجاد می‌کند. بعد Service Providerها ثبت و Boot می‌شوند. HTTP Kernel درخواست را دریافت می‌کند و آن را از Pipeline Middlewareها عبور می‌دهد. سپس Router مسیر مناسب را پیدا می‌کند، Controller از طریق Service Container ساخته می‌شود، متد Controller اجرا می‌شود و Response تولید و به مرورگر ارسال می‌شود. در پایان متد terminate() برای کارهای پس از ارسال پاسخ اجرا می‌شود.»

این پاسخ در مصاحبه واقعاً امتیاز بالایی دارد.

مرحله بعدی که به نظر من مهم‌ترین بخش Laravel Internals است، Service Container و تفاوت bind()، singleton() و make() است؛ آن بخش معمولاً حداقل ۳۰٪ سؤالات Laravel Internals را تشکیل می‌دهد.

بخش دوم – Service Container

Service Container چیست؟

Service Container یک IoC Container (Inversion of Control Container) است که مسئول ساخت (resolve) و مدیریت وابستگی‌های کلاس‌ها است.

تعریف مصاحبه‌ای: Service Container یک کلاس مرکزی در Laravel است که وظیفه‌ی Dependency Resolution و Dependency Injection را بر عهده دارد.

به زبان ساده:

به جای اینکه خودت با new کلاس‌ها را بسازی، Laravel آن‌ها را برایت می‌سازد.

بدون Service Container

class PaymentService
{
}

class OrderService
{
    private PaymentService $payment;

    public function __construct()
    {
        $this->payment = new PaymentService();
    }
}

مشکل:

  • وابستگی شدید
  • تست سخت
  • جایگزینی پیاده‌سازی سخت

با Service Container

class OrderService
{
    public function __construct(
        private PaymentService $payment
    ) {
    }
}

اینجا OrderService خودش PaymentService را نمی‌سازد. Laravel این کار را انجام می‌دهد.

Container چگونه Resolve می‌کند؟

فرض کن:

class PaymentService
{
}

class OrderService
{
    public function __construct(
        PaymentService $payment
    ) {
    }
}

وقتی بنویسی:

$orderService = app()->make(OrderService::class);

Laravel این مراحل را انجام می‌دهد:

  1. Reflection روی OrderService
  2. بررسی Constructor
  3. پیدا کردن PaymentService
  4. ساخت PaymentService
  5. تزریق آن به Constructor
  6. برگرداندن OrderService

یعنی:

OrderService
│
▼
PaymentService

Container
↓
new PaymentService()
↓
new OrderService($payment)

app() چیست؟

در Laravel: app() همان Application Container است.

مثلاً:

app()->make(PaymentService::class);
// یا:
resolve(PaymentService::class);
// یا:
app(PaymentService::class);

همه تقریباً یک کار انجام می‌دهند.

make() چیست؟

make() یعنی: این کلاس را برای من Resolve کن.

مثلاً:

$payment = app()->make(
    PaymentService::class
);

اگر کلاس وابستگی داشته باشد:

class PaymentService
{
    public function __construct(
        Logger $logger
    ) {
    }
}

Container اول Logger را می‌سازد. بعد PaymentService را می‌سازد.

bind() چیست؟

اینجا بخش مهم مصاحبه است.

فرض کن Interface داریم.

interface PaymentGateway
{
    public function pay(float $amount): bool;
}

پیاده‌سازی:

class StripeGateway implements PaymentGateway
{
    public function pay(float $amount): bool
    {
        return true;
    }
}

Container نمی‌تواند Interface را Instantiate کند.

این کد خطا می‌دهد:

app()->make(PaymentGateway::class);

چون Interface قابل ساخت نیست. باید Binding تعریف کنیم.

$this->app->bind(
    PaymentGateway::class,
    StripeGateway::class
);

حالا:

app()->make(PaymentGateway::class);

خروجی: یک شیء از StripeGateway.

bind() چه کاری می‌کند؟ به Container می‌گوید: هر وقت کسی PaymentGateway خواست، StripeGateway را بساز.

bind() و singleton()

این مهم‌ترین سؤال مصاحبه است.

bind() – هر بار یک نمونه‌ی جدید می‌سازد. 

$this->app->bind(
    PaymentGateway::class,
    StripeGateway::class
);

$a = app(PaymentGateway::class);
$b = app(PaymentGateway::class);

var_dump($a === $b); // false

دو شیء متفاوت.

singleton() – فقط یک بار ساخته می‌شود. 

$this->app->singleton(
    PaymentGateway::class,
    StripeGateway::class
);

$a = app(PaymentGateway::class);
$b = app(PaymentGateway::class);

var_dump($a === $b); // true

همان شیء برگردانده می‌شود.

چه زمانی singleton؟ برای سرویس‌هایی که State مشترک دارند. مثلاً:

  • Config Repository
  • Cache Manager
  • Logger
  • Redis Connection
  • API Client

مثال واقعی

$this->app->singleton(
    PaymentGateway::class,
    function ($app) {
        return new StripeGateway(
            $app['config']['services.stripe.key']
        );
    }
);

اینجا از Closure استفاده کردیم. چرا؟ چون ساخت شیء پیچیده است.

bind با Closure

$this->app->bind(
    PaymentGateway::class,
    function ($app) {
        return new StripeGateway(
            $app->make(Logger::class)
        );
    }
);

داخل Closure هم می‌توانیم از Container استفاده کنیم.

Resolution Chain

فرض کن:

OrderService
↓
PaymentGateway
↓
StripeGateway
↓
HttpClient
↓
Logger

وقتی app(OrderService::class) را اجرا می‌کنی، Container کل درخت وابستگی را می‌سازد. به این می‌گویند: Dependency Graph Resolution

سؤال مصاحبه

تفاوت bind و singleton چیست؟

bind() در هر Resolve یک نمونه‌ی جدید ایجاد می‌کند، اما singleton() اولین بار شیء را ایجاد می‌کند و همان نمونه را در تمام درخواست‌های بعدی برمی‌گرداند.

سؤال مهم‌تر

اگر PaymentGateway Interface باشد، Laravel چگونه می‌فهمد StripeGateway را Inject کند؟

از طریق Binding در Service Container که معمولاً در Service Provider تعریف می‌شود.

مثلاً:

public function register()
{
    $this->app->bind(
        PaymentGateway::class,
        StripeGateway::class
    );
}

پاسخ کامل مصاحبه

Service Container چیست؟

Service Container هسته‌ی Dependency Injection در Laravel است. این Container مسئول Resolve کردن کلاس‌ها و وابستگی‌های آن‌ها است. با استفاده از Reflection می‌تواند کلاس‌ها را به صورت خودکار Instantiate کند و از طریق bind() و singleton() Interfaceها را به پیاده‌سازی‌های مناسب متصل کند. این مکانیزم باعث کاهش Coupling، افزایش تست‌پذیری و اجرای Dependency Inversion Principle می‌شود.

Dependency Injection

نکته‌ی مهم این است که Service Container و Dependency Injection دو مفهوم متفاوت هستند؛ خیلی‌ها این دو را یکی می‌دانند.

Dependency Injection یک الگوی طراحی (Design Pattern) است. Service Container ابزاری است که Laravel برای اجرای Dependency Injection فراهم کرده است.

Dependency Injection چیست؟

به جای اینکه یک کلاس وابستگی‌های خودش را بسازد، وابستگی‌ها از بیرون به آن تزریق (Inject) می‌شوند.

❌ بدون Dependency Injection

class PaymentService
{
    public function pay(float $amount): bool
    {
        return true;
    }
}

class OrderService
{
    private PaymentService $payment;

    public function __construct()
    {
        $this->payment = new PaymentService();
    }

    public function checkout()
    {
        return $this->payment->pay(1000);
    }
}

مشکل چیست؟ OrderService خودش PaymentService را می‌سازد. این یعنی Tight Coupling.

مشکلات این طراحی:

  • تست سخت – چون همیشه PaymentService واقعی ساخته می‌شود.
  • تغییر سخت – اگر بخواهیم Stripe را به Zarinpal تغییر دهیم، باید OrderService را تغییر دهیم.
  • وابستگی شدید – OrderService دقیقاً می‌داند PaymentService چگونه ساخته می‌شود.

✅ با Dependency Injection

class OrderService
{
    public function __construct(
        private PaymentService $payment
    ) {
    }

    public function checkout()
    {
        return $this->payment->pay(1000);
    }
}

الان OrderService فقط از PaymentService استفاده می‌کند. ساختن PaymentService مسئولیت OrderService نیست.

چه کسی PaymentService را می‌سازد؟ Laravel Service Container.

وقتی app(OrderService::class) را اجرا می‌کنی، Container این کار را انجام می‌دهد:

new PaymentService()
↓
new OrderService($paymentService)

انواع Dependency Injection

سه نوع اصلی وجود دارد.

۱. Constructor Injection (مهم‌ترین)

رایج‌ترین روش در Laravel.

class OrderService
{
    public function __construct(
        private PaymentService $payment
    ) {
    }
}

مزایا:

  • وابستگی اجباری است.
  • Immutable می‌شود.
  • تست راحت‌تر است.
  • واضح است.

در Laravel بهترین روش همین است.

۲. Method Injection

Laravel از این روش هم استفاده می‌کند. مثلاً در Controller:

class OrderController
{
    public function store(
        PaymentService $payment
    ) {
        $payment->pay(1000);
    }
}

Laravel هنگام اجرای متد، PaymentService را Inject می‌کند. این بسیار رایج است.

۳. Setter Injection

کمتر استفاده می‌شود.

class OrderService
{
    private PaymentService $payment;

    public function setPaymentService(
        PaymentService $payment
    ) {
        $this->payment = $payment;
    }
}

مشکل: ممکن است فراموش کنیم set را صدا بزنیم. به همین دلیل در Laravel معمولاً Constructor Injection ترجیح داده می‌شود.

Dependency Injection با Interface

اینجا بخش مهم مصاحبه است.

interface PaymentGateway
{
    public function pay(float $amount): bool;
}

class StripeGateway implements PaymentGateway
{
    public function pay(float $amount): bool
    {
        return true;
    }
}

class OrderService
{
    public function __construct(
        private PaymentGateway $gateway
    ) {
    }
}

سؤال: Laravel چگونه PaymentGateway را Inject می‌کند؟

از طریق Binding. 
$this->app->bind(
    PaymentGateway::class,
    StripeGateway::class
);
وقتی OrderService ساخته می‌شود: Container می‌بیند PaymentGateway لازم است. Binding وجود دارد. StripeGateway را می‌سازد. Inject می‌کند.

چرا Constructor Injection بهتر است؟

این سؤال خیلی رایج است.

  • دلیل اول: وابستگی‌ها مشخص هستند – با نگاه به Constructor می‌فهمی کلاس به چه چیزهایی نیاز دارد.
  • دلیل دوم: جلوگیری از Null – اگر Dependency Inject نشود، اصلاً کلاس ساخته نمی‌شود.
  • دلیل سوم: تست – به راحتی Mock تزریق می‌شود.
$mock = Mockery::mock(PaymentGateway::class);
$service = new OrderService($mock);

ارتباط DI با DIP

Dependency Injection ابزار اجرای Dependency Inversion Principle است. DIP می‌گوید: به Interface وابسته شو. DI می‌گوید: آن Interface را از بیرون تزریق کن.

سؤال مهم مصاحبه

تفاوت Dependency Injection و Service Container چیست؟

Dependency Injection یک الگوی طراحی است که وابستگی‌ها را از بیرون به کلاس تزریق می‌کند. Service Container مکانیزمی در Laravel است که این وابستگی‌ها را Resolve و Inject می‌کند. یعنی DI = Principle / Pattern و Container = Implementation.

سؤال مهم‌تر

آیا Laravel بدون Service Container هم Dependency Injection دارد؟

بله. مثلاً: 
$payment = new PaymentService();
$order = new OrderService($payment);
این هم Dependency Injection است. فقط دستی انجام شده است. Laravel این کار را به صورت خودکار انجام می‌دهد.

پاسخ حرفه‌ای مصاحبه

Dependency Injection چیست و چه مزیتی دارد؟

Dependency Injection یعنی وابستگی‌های یک کلاس از بیرون به آن تزریق شوند، نه اینکه داخل کلاس ساخته شوند. در Laravel معمولاً از Constructor Injection استفاده می‌کنیم و Service Container مسئول Resolve کردن وابستگی‌ها است. این کار باعث کاهش Coupling، افزایش تست‌پذیری، رعایت Dependency Inversion Principle و امکان جایگزینی پیاده‌سازی‌ها بدون تغییر کلاس مصرف‌کننده می‌شود.

Service Providers

Bindingها را کجا تعریف می‌کنید؟ پاسخ: Service Providers.

Service Providers محل ثبت (register) و راه‌اندازی (boot) سرویس‌های Laravel هستند.

تقریباً تمام قابلیت‌های Laravel (Routing، Events، Auth، Validation، Queue، Cache و...) از طریق Service Providerها به برنامه متصل می‌شوند.

Service Provider چیست؟

از Illuminate\Support\ServiceProvider ارث‌بری می‌کند.

namespace App\Providers;

use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register()
    {
    }

    public function boot()
    {
    }
}

دو متد مهم دارد: register() و boot(). این دو را باید کاملاً بفهمی.

نقش register()

register() برای ثبت سرویس‌ها در Service Container است. اینجا Binding انجام می‌دهیم.

مثال:

interface PaymentGateway
{
    public function pay(float $amount): bool;
}

class StripeGateway implements PaymentGateway
{
    public function pay(float $amount): bool
    {
        return true;
    }
}

class AppServiceProvider extends ServiceProvider
{
    public function register()
    {
        $this->app->bind(
            PaymentGateway::class,
            StripeGateway::class
        );
    }
}

الان هر جا PaymentGateway Inject شود، Laravel StripeGateway را تزریق می‌کند.

نقش boot()

boot() برای راه‌اندازی سرویس‌ها بعد از ثبت همه Providerها است. یعنی وقتی تمام Bindingها انجام شد، boot() اجرا می‌شود.

مثال:

public function boot()
{
    View::share('appName', config('app.name'));
}

یا

use Illuminate\Support\Facades\Route;

public function boot()
{
    Route::pattern('id', '[0-9]+');
}

ترتیب اجرا

این سؤال مصاحبه‌ای مهم است.

Laravel ابتدا register همه Providerها را اجرا می‌کند. بعد boot همه Providerها را اجرا می‌کند.

Provider A register
Provider B register
Provider C register
↓
Provider A boot
Provider B boot
Provider C boot

دلیل این طراحی چیست؟ چون در boot() ممکن است به سرویس Provider دیگری نیاز داشته باشی. اگر اول boot اجرا می‌شد، شاید آن سرویس هنوز ثبت نشده بود.

مثال مهم

فرض کن:

Provider اول:

public function register()
{
    $this->app->singleton(
        PaymentGateway::class,
        StripeGateway::class
    );
}

Provider دوم:

public function boot()
{
    $gateway = app(PaymentGateway::class);
}

این کار درست است. چون register() قبلاً اجرا شده است.

چه چیزهایی در register؟

قانون مهم: در register() فقط Binding انجام بده. مثل: bind, singleton, scoped, instance 

public function register()
{
    $this->app->singleton(
        PaymentGateway::class,
        StripeGateway::class
    );
}

چه چیزهایی در boot؟

در boot() کارهایی که به سرویس‌های دیگر وابسته‌اند. مثل: Route, View Composer, Model Observer, Validation Rule, Event Listener, Blade Directive

مثال Observer:

use App\Models\Order;
use App\Observers\OrderObserver;

public function boot()
{
    Order::observe(OrderObserver::class);
}

اگر این را در register بنویسی، ممکن است مشکل ایجاد شود.

مثال واقعی AppServiceProvider

class AppServiceProvider extends ServiceProvider
{
    public function register()
    {
        $this->app->bind(
            PaymentGateway::class,
            StripeGateway::class
        );

        $this->app->singleton(
            ExchangeRateService::class,
            function ($app) {
                return new ExchangeRateService(
                    config('services.exchange.key')
                );
            }
        );
    }

    public function boot()
    {
        Order::observe(OrderObserver::class);

        View::share(
            'appName',
            config('app.name')
        );
    }
}

این یک نمونه‌ی مصاحبه‌ای خوب است.

چرا Binding را در register انجام می‌دهیم؟

چون Service Container در مرحله‌ی ساخت Application به Bindingها نیاز دارد. اگر Binding را در boot انجام دهی، ممکن است بعضی سرویس‌ها قبل از آن Resolve شوند.

سؤال مهم مصاحبه

تفاوت register و boot چیست؟

register() برای ثبت سرویس‌ها و Bindingها در Service Container است و باید فقط عملیات Registration انجام دهد. boot() بعد از ثبت تمام Providerها اجرا می‌شود و برای راه‌اندازی سرویس‌ها، ثبت Observerها، View Composerها، Route Patternها و سایر تنظیماتی که به سرویس‌های دیگر وابسته هستند استفاده می‌شود.

سؤال بعدی

اگر بخواهم PaymentGateway را به StripeGateway Bind کنم، در register می‌نویسم یا boot؟

register، چون Binding مربوط به Container است.

سؤال مهم‌تر

آیا می‌توانیم در boot از Service Container استفاده کنیم؟

بله. مثلاً: 
public function boot()
{
    $gateway = app(PaymentGateway::class);
}
چون در این مرحله همه Providerها Register شده‌اند.

ارتباط با Facades

وقتی می‌نویسی: Cache::get('key'); این Facade از طریق Service Provider مربوط به Cache ثبت شده است. یعنی پشت Facadeها هم Service Provider وجود دارد.

پاسخ کامل مصاحبه

Service Provider چیست؟

Service Provider نقطه‌ی مرکزی Bootstrapping در Laravel است. از طریق register() سرویس‌ها و Interface Bindingها را در Service Container ثبت می‌کنیم و از طریق boot() بعد از ثبت تمام Providerها، سرویس‌ها را راه‌اندازی می‌کنیم؛ مانند ثبت Observerها، View Composerها، Route Patternها و سایر تنظیمات وابسته به Container.

اگر داخل boot() یک Interface را Bind کنیم، چه مشکلی ممکن است ایجاد شود؟

ممکن است قبل از اجرای boot() آن Interface Resolve شده باشد، بنابراین Binding دیر انجام می‌شود. به همین دلیل Bindingها باید در register() انجام شوند.

Facade چیست؟ آیا واقعاً Static است؟

اگر این سؤال را خوب جواب بدهی، نشان می‌دهد که Service Container، Static Method، و Laravel Internals را فهمیده‌ای.

Facade چیست؟

تعریف ساده: Facade یک Proxy (واسط) است که دسترسی راحت به سرویس‌های داخل Service Container را فراهم می‌کند.

وقتی می‌نویسی:

Cache::get('key');
Auth::user();
Log::info('message');
DB::table('users')->get();

در ظاهر شبیه متد Static است. اما در واقع Static واقعی نیست. این مهم‌ترین نکته‌ی مصاحبه است.

تصور اشتباه

بعضی‌ها فکر می‌کنند Cache::get('key'); یعنی:

class Cache
{
    public static function get($key)
    {
    }
}

اما این درست نیست.

پشت صحنه

Facade در Laravel یک کلاس است که از Illuminate\Support\Facades\Facade ارث‌بری می‌کند. 

class Cache extends Facade
{
    protected static function getFacadeAccessor()
    {
        return 'cache';
    }
}

این متد getFacadeAccessor() بسیار مهم است. این متد می‌گوید: وقتی کسی Cache::get() را صدا زد، برو سرویس 'cache' را از Container بگیر.

اتفاق واقعی

وقتی می‌نویسی Cache::get('key'); تقریباً این اتفاق می‌افتد: 

$cache = app('cache');
$cache->get('key');

یعنی Facade فقط یک میانبر است.

چرا Static به نظر می‌رسد؟

Facade از متد جادویی PHP استفاده می‌کند: __callStatic()

داخل کلاس پایه Facade:

public static function __callStatic($method, $args)
{
    $instance = static::resolveFacadeInstance(
        static::getFacadeAccessor()
    );

    return $instance->$method(...$args);
}

پس Cache::get('key'); تبدیل می‌شود به $instance->get('key'); روی شیء واقعی.

ارتباط با Service Container

اینجا Facade به Container وصل می‌شود.

Cache::get()
↓
Facade
↓
Service Container
↓
CacheManager instance

بنابراین Facade بدون Container کار نمی‌کند.

مثال با DB

وقتی DB::table('users')->get(); را اجرا می‌کنی، Facade 'db' را از Container می‌گیرد. آن سرویس Connection یا Database Manager است. بعد table() روی آن شیء اجرا می‌شود.

مزیت Facade

  • کد کوتاه: به جای $cache = app('cache'); $cache->get('key'); می‌نویسی Cache::get('key');
  • خوانایی: Log::info();, Cache::put();, Storage::disk(); واضح‌تر است.

آیا Facade با Dependency Injection تضاد دارد؟

این سؤال مهم مصاحبه است. جواب: نه، ولی Trade-off دارد.

مثال DI:

class OrderService
{
    public function __construct(
        private CacheRepository $cache
    ) {
    }
}

وابستگی واضح است.

آیا Facade واقعاً Static است؟

خیر. Facade فقط ظاهری Static دارد. متدهای آن از طریق __callStatic به یک شیء واقعی که داخل Service Container Resolve می‌شود Delegate می‌شوند.

سؤال بعدی

تفاوت Facade و Helper Function چیست؟

cache('key');
Cache::get('key');

Facade: قابل Mock, قابل Extend, وابسته به Container. Helper: تابع معمولی، معمولاً Wrapper ساده.

Middleware

Middleware یک Filter یا Pipeline Layer است که درخواست HTTP را قبل از رسیدن به Controller پردازش می‌کند و می‌تواند درخواست را ادامه دهد، تغییر دهد یا متوقف کند.

نقش Closure $next

public function handle(
    Request $request,
    Closure $next
) {
    return $next($request);
}

$next یعنی: درخواست را به Middleware بعدی یا Controller ارسال کن.

اگر $next را صدا نزنی، درخواست متوقف می‌شود.

public function handle(Request $request, Closure $next) {
    return response()->json([
        'message' => 'Blocked'
    ], 403);
}

Controller هرگز اجرا نمی‌شود.

مثال Authentication

public function handle(Request $request, Closure $next) {
    if (!$request->user()) {
        return redirect('/login');
    }

    return $next($request);
}

اگر کاربر Login نباشد: درخواست متوقف می‌شود. Redirect انجام می‌شود. اگر Login باشد: Middleware بعدی اجرا می‌شود.

Before Middleware

این نوع Middleware قبل از Controller اجرا می‌شود.

public function handle(Request $request, Closure $next) {
    Log::info('Request started');
    return $next($request);
}
Request
↓
Log
↓
Controller

After Middleware

می‌توانیم بعد از اجرای Controller هم کد اجرا کنیم.

public function handle(Request $request, Closure $next) {
    $response = $next($request);
    $response->headers->set('X-App', 'Laravel');
    return $response;
}
Request
↓
Controller
↓
Modify Response
↓
Response

این بسیار مهم است.

Global Middleware

روی همه درخواست‌ها اجرا می‌شود. مثال: TrustProxies, HandleCors, PreventRequestsDuringMaintenance, ValidatePostSize, TrimStrings. در نسخه‌های جدید Laravel در فایل Bootstrap ثبت می‌شوند.

Route Middleware

فقط روی Routeهای مشخص اجرا می‌شود.

Route::get('/admin', function () {
    //
})->middleware('auth');

Middleware Parameter

Laravel اجازه می‌دهد پارامتر ارسال کنیم.

Route::get('/admin')->middleware('role:admin');

public function handle(Request $request, Closure $next, string $role) {
    if ($request->user()->role !== $role) {
        abort(403);
    }
    return $next($request);
}

Middleware Priority

گاهی ترتیب اجرا مهم است. مثلاً Session, Authentication, Authorization. اگر Authorization قبل از Authentication اجرا شود، مشکل ایجاد می‌شود. Laravel برای بعضی Middlewareها Priority مشخص می‌کند.

Terminable Middleware

این یکی سؤال سطح Mid-Level است. بعضی Middlewareها بعد از ارسال Response هم اجرا می‌شوند. 

class LogRequestTime
{
    public function handle($request, Closure $next) {
        return $next($request);
    }

    public function terminate($request, $response) {
        Log::info('Request finished');
    }
}
Request
↓
Controller
↓
Response sent
↓
terminate()

این برای: Logging, Analytics, Cleanup مناسب است.

ارتباط با Pipeline Pattern

Laravel Middleware بر پایه Pipeline Pattern ساخته شده است. هر Middleware: Request را دریافت می‌کند. کاری انجام می‌دهد. Request را به مرحله بعد می‌دهد.

تفاوت Middleware و Controller

Middleware: احراز هویت, Rate Limiting, CORS, Logging, Permission, Locale. Controller: Business Logic, Database, Payment, Response. Middleware نباید منطق اصلی برنامه را انجام دهد.

سؤال مهم مصاحبه

چرا از Middleware استفاده می‌کنیم؟

برای جدا کردن Cross-Cutting Concerns از Business Logic.

مثلاً بد:

class OrderController
{
    public function index()
    {
        if (!auth()->check()) {
            abort(401);
        }
        // ...
    }
}

خوب:

Route::middleware('auth')
    ->group(function () {
        Route::get('/orders', [OrderController::class, 'index']);
    });

Authentication از Controller خارج شده است.

Middleware چیست و نقش $next چیست؟

Middleware یک لایه بین Request و Controller است که می‌تواند درخواست را بررسی، تغییر یا متوقف کند. متد handle() درخواست را دریافت می‌کند و Closure $next نماینده مرحله بعدی Pipeline است. با فراخوانی $next($request) درخواست به Middleware بعدی یا Controller ارسال می‌شود و بعد از دریافت Response نیز می‌توان آن را تغییر داد.

تفاوت handle() و terminate() در Middleware چیست؟

handle() قبل و در حین پردازش درخواست اجرا می‌شود، اما terminate() بعد از ارسال Response به کاربر اجرا می‌شود و برای کارهای پس‌زمینه مثل Logging و Analytics مناسب است.

Validation در Laravel

ساده‌ترین روش:

public function store(Request $request)
{
    $validated = $request->validate([
        'name' => 'required|string|max:255',
        'email' => 'required|email|unique:users,email',
        'password' => 'required|min:8',
    ]);

    User::create($validated);
}

اگر Validation شکست بخورد، Laravel به صورت خودکار: Redirect (در Web) یا JSON Error (در API) برمی‌گرداند. این رفتار خودکار یکی از مزیت‌های Laravel است.

مهم‌ترین Ruleها

این‌ها را باید حفظ نباشی، ولی روان استفاده کنی.

Validation با آرایه

$request->validate([
    'items' => 'required|array',
    'items.*.product_id' => 'required|exists:products,id',
    'items.*.quantity' => 'required|integer|min:1',
]);

Form Request چیست؟

یک کلاس جدا برای Validation و Authorization.

class StoreUserRequest extends FormRequest
{
    public function authorize(): bool
    {
        return true;
    }

    public function rules(): array
    {
        return [
            'name' => 'required|string|max:255',

        ];

Controller:

public function store(StoreUserRequest $request)
{
    User::create($request->validated());
}

خیلی تمیزتر شد.

authorize()

این متد بسیار مهم است. اینجا می‌توانی مجوز دسترسی را بررسی کنی.

public function authorize(): bool
{
    return auth()->user()->isAdmin();
}

اگر false برگرداند، Laravel به صورت خودکار برمی‌گرداند. این یعنی Authorization قبل از Controller انجام می‌شود.

rules()

تمام Ruleها اینجا قرار می‌گیرند.

public function rules(): array
{
    return [
        'title' => 'required|string|max:255',
        'content' => 'required|string',
        'category_id' => 'required|exists:categories,id',
    ];
}

validated()

بعد از Validation: $data = $request->validated(); فقط داده‌های معتبر را برمی‌گرداند. این از نظر امنیتی بهتر است.

تفاوت validated() و all() – all() تمام داده‌ها را برمی‌گرداند، اما validated() فقط داده‌هایی که Validation شده‌اند.

چگونه هنگام Update از unique استفاده کنیم؟

کاربر ایمیل خودش را هم نمی‌تواند ذخیره کند.

use Illuminate\Validation\Rule;

'email' => [
    'required',
    'email',
    Rule::unique('users', 'email')
        ->ignore($this->route('user')),
]

Custom Messages

public function messages(): array
{
    return [
        'name.required' => 'نام الزامی است',
        'email.email' => 'ایمیل معتبر نیست',
    ];

Custom Attributes

public function attributes(): array
{
    return [
        'email' => 'آدرس ایمیل',

prepareForValidation()

یکی از سؤالات سطح Mid-Level. قبل از Validation اجرا می‌شود.

protected function prepareForValidation()
{
    $this->merge([
        'email' => strtolower($this->email),
        'slug' => Str::slug($this->title),

}

کاربرد: Trim, Lowercase, Generate Slug, Merge Data

passedValidation()

بعد از موفقیت Validation اجرا می‌شود.

protected function passedValidation()
{
    $this->replace([
        'name' => strtoupper($this->name),

}

کمتر استفاده می‌شود.

امنیت و Sanctum

Laravel چه مکانیزم‌هایی برای امنیت دارد؟

Laravel برای جلوگیری از SQL Injection از Prepared Statement در Eloquent و Query Builder استفاده می‌کند، برای Mass Assignment از $fillable و $guarded، برای CSRF از Token، برای XSS از Blade Escaping، برای Passwordها از Hashing مانند bcrypt و argon2، و برای جلوگیری از Abuse از Rate Limiting استفاده می‌کند.

Sanctum بهتر است یا JWT؟

بستگی به معماری دارد. برای اکثر APIهای Laravel، SPA و Mobile ساده، Sanctum انتخاب مناسب‌تری است چون با Laravel هماهنگ است. JWT زمانی مناسب است که نیاز به Stateless Authentication یا معماری‌های توزیع‌شده داشته باشیم.

Gates, Policies, Authorization

سه ابزار مهم: Gates, Policies, Middleware

Gate چیست؟

Gate برای Authorization ساده است. مثال: آیا کاربر می‌تواند Delete Post کند؟ در AuthServiceProvider تعریف می‌شود. 

Gate::define('delete-post', function ($user, $post) {
    return $user->id === $post->user_id;
});

استفاده: Gate::allows('delete-post', $post)

Policy کلاس مخصوص Authorization برای یک Model است. مثلاً PostPolicy. متدها: view(), create(), update(), delete().

مثال داخل Policy:

public function update(User $user, Post $post)
{
    return $user->id === $post->user_id;
}

یعنی فقط صاحب Post می‌تواند Update کند.

چرا Policy بهتر از گذاشتن شرط داخل Controller است؟

من در قسمت پروژه خودم چطور از policy , laravel-permission استفاده کردم

Repository, Service, Factory Patterns

Repository Pattern

Repository مسئولیت ذخیره داده‌ها.

مثال:

interface UserRepository
{
    public function find(int $id): User;
}

class EloquentUserRepository implements UserRepository
{
    public function find(int $id): User
    {
        return User::findOrFail($id);
    }
}

Service:

class UserService
{
    public function __construct(
        private UserRepository $users
    ) {
    }

    public function getUser(int $id): User
    {
        return $this->users->find($id);
    }
}

Binding:

$this->app->bind(
    UserRepository::class,
    EloquentUserRepository::class
);

مزایا: DIP, تست‌پذیری, امکان جایگزینی Data Source, جداسازی Persistence Logic

سؤال مصاحبه: آیا همیشه Repository لازم است؟

خیر. اگر فقط Wrapper ساده روی Eloquent باشد: find(), all(), create() – ارزش زیادی ندارد. Repository زمانی مفید است که: Queryهای پیچیده, چند منبع داده, Cache, External API, Domain Logic وجود داشته باشد.

Service Layer Pattern

این Pattern در Laravel بسیار رایج است.

مشکل – Controller:

public function store(Request $request)
{
    DB::transaction(function () use ($request) {
        $order = Order::create(...);
        Payment::charge(...);
        Notification::send(...);
        Log::info(...);
    });
}

Business Logic داخل Controller است.

Service Layer:

class OrderService
{
    public function createOrder(array $data): Order
    {
        return DB::transaction(function () use ($data) {
            $order = Order::create($data);
            $this->payment->charge($order);
            $this->notification->send($order);
            return $order;
        });
    }
}

Controller:

class OrderController
{
    public function store(
        StoreOrderRequest $request,
        OrderService $service
    ) {
        return $service->createOrder(
            $request->validated()
        );
    }
}

مسئولیت‌ها:

  • Controller: HTTP, Validation, Response
  • Service: Business Logic, Transaction, Coordination
  • Repository: Database

این تفکیک بسیار مهم است.

Repository + Service

بهترین ترکیب:

|
↓

↓

|
↓

Controller به دیتابیس دست نمی‌زند.

Factory Pattern

Factory برای ساخت Object استفاده می‌شود. در Laravel دو نوع Factory مهم است.

  • Database Factory – برای Testing و Seeding: User::factory()->count(10)->create();
  • Object Factory – مثلاً Payment Gateway.
interface PaymentGateway
{
    public function pay();
}

class StripeGateway implements PaymentGateway { public function pay() {} }
class ZarinpalGateway implements PaymentGateway { public function pay() {} }

class PaymentFactory
{
    public function make(string $driver): PaymentGateway
    {
        return match ($driver) {
            'stripe' => new StripeGateway(),
            'zarinpal' => new ZarinpalGateway(),
        };
    }
}

استفاده: $gateway = $factory->make('stripe'); $gateway->pay();

Factory vs Service Container

این سؤال مهم است. Factory: تصمیم می‌گیرد کدام Object ساخته شود. Container: وابستگی‌ها را Resolve می‌کند. Factory معمولاً داخل Service Layer استفاده می‌شود.

سؤال مصاحبه: Repository و Service چه تفاوتی دارند؟

Repository مسئول دسترسی به داده است، اما Service مسئول Business Logic و هماهنگی بین چند Repository یا سرویس دیگر است.

مثال: Repository: findUser(), saveUser(), getActiveUsers(). Service: registerUser(), purchaseSubscription(), createOrder().

    }

چرا از Service Layer استفاده می‌کنید؟

برای جدا کردن Business Logic از HTTP Layer. Controller فقط درخواست و پاسخ را مدیریت می‌کند، اما منطق اصلی برنامه، Transactionها، هماهنگی بین Repositoryها، Queue، Notification و سایر عملیات در Service Layer قرار می‌گیرد. این کار باعث رعایت SRP، افزایش تست‌پذیری و Maintainability می‌شود.
